# V0.7 Full-file Response Analysis

## Goal

Upgrade response-time processing from a single extracted current step to a complete-file workflow. One BMW response file may contain the four current transitions Soft→Hard, Soft→Medium, Hard→Medium and Hard→Soft, each measured in rebound and compression. The analyzer must detect every valid transition in the file and keep each direction as an independent result.

## Segmentation

1. Read the entire time series.
2. Smooth only the current feedback enough to reject high-frequency noise; do not overwrite raw current.
3. Detect every current-step transition using local current derivative candidates plus pre/post plateau verification.
4. Reject candidates whose verified current change is below the configured minimum step.
5. Build an event window around each transition using the midpoint to neighboring transitions, while calculating start/end current from local stable windows around that transition rather than from the whole file.
6. Use load sign for the response direction requested by the engineering convention: positive load = Rebound, negative load = Compression. Velocity sign remains a QA cross-check only.

## BMW stage naming

The numeric current transition is always retained. For files with three repeatable damping states, the software additionally derives Soft / Medium / Hard state labels from the average absolute damping-force magnitude associated with each current plateau. This avoids hard-coding a particular current polarity. Lowest force magnitude is Soft, highest is Hard, and the intermediate state is Medium. If the mapping is ambiguous, the result falls back to numeric current labels rather than guessing.

## Result rows

Each current step becomes one row containing at least:

- Event ID
- Stage / numeric current transition
- Current start/end/10%
- Direction (Rebound + / Compression -)
- target speed and measured speed at switching
- t₀, t₁%, t₆₃%, t₉₀%
- F0, F1, F63, F90, F100
- sample rate, status and QA issues

## Target-speed lines

The OEM profile and target-speed list are independent settings. BMW and Audi provide defaults, while the operator may enter any positive finite customer speeds such as 0.1, 0.3, 0.6 and 1.0 m/s. Target speed is matched only when measured switching speed is reasonably close. The plot keeps the measured velocity sign and draws the target-speed line at the corresponding signed level.

## Plot specification

Three synchronized plots share the time axis.

### Current-Time

- raw current curve visibly thicker
- dashed horizontal I₁₀% and I₁₀₀% lines
- enlarged labels above the dashed references
- dashed vertical t0 line

### Force-Time

- damping-force curve visibly thicker
- large direction annotation `Rebound (+)` or `Compression (-)`
- dashed horizontal F₁%, F₆₃%, F₉₀%, F₁₀₀% lines that intersect the displayed measured trace
- dashed vertical t₁%, t₆₃% and t₉₀% lines
- enlarged level labels above horizontal lines and calculated time labels offset from vertical markers

### Velocity-Time

- thicker velocity curve
- dashed target-speed horizontal line with target-speed label
- dashed t0 vertical line

All reference/marker lines are dashed. Text and axes must remain readable on both white and dark plot backgrounds.

## UI

- full result table contains all detected events
- event selector displays stage, direction and current transition
- selecting a table row also switches the displayed event
- no customer PASS/FAIL is invented without a configured limit

## Validation

Synthetic regression data must contain eight response events (four current transitions × rebound/compression) and prove that all eight are detected and classified. Existing single-event response and hysteresis tests must remain green.
